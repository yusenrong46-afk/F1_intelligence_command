M7 is structurally sound and safety-ready for the benchmarked cities. The key design decision is correct: extraction is a candidate generator, while deterministic verification is the authority. The fresh runs, adversarial tests, proposal cases, and dashboard/chatbot policy checks all support that boundary.

System Understanding

M7 packages matrix-aware extraction on google/gemini-3.1-flash-lite, source repair, deterministic verification, M7 scored measurement, GIS exports, and the Civic Console dashboard. The product path is: run_m7_bakeoff.py -> run_m7_bakeoff_engine.py --discovery-mode exhaustive -> native extraction -> slim_pipeline.py -> verifier outputs.

What works: the trust boundary is explicit in docs, code, tests, and output contracts. decision_policy.py centralizes final bucket policy rather than scattering promotion decisions.
What remains fragile: table-heavy bylaws still depend too much on flattened text and LLM candidate phrasing. Surrey exposed this immediately through operator and scope uncertainty.

M7.5 Upgrade Plan

Extraction

  • Add a city onboarding harness: fetch PDF, hash it, detect relevant zone pages, create provenance, run dry extraction, suggest gold candidates, and refuse precision scoring until gold is marked complete.
  • Use schema-constrained extraction: validate every model pack against JSON schema, retry invalid JSON at pack scope, and classify errors by pack, page, table row, and family.
  • Bring layout into evidence: add visual/table page snapshots and ColPali-style shadow retrieval for page/table recall. Do not let it verify; use it to retrieve better evidence for deterministic proof.
  • Adopt DocETL-style decomposition: split “extract all rules” into family-specific, table-specific, branch-condition, and footnote tasks, then compare plans through the benchmark.

Verification

  • Keep the verifier strict: no prompt change should promote a rule unless value, unit, operator, scope, applies_to, condition, and exception support are explicit.
  • Improve table proof, not text looseness: preserve row/column headings, footnotes, and branch labels so Surrey-style setbacks can verify safely instead of landing in operator/scope review.
  • Expand adversarial generation: auto-create traps from every new gold rule: direction flips, wrong row, wrong column, missing unit, exception ignored, and cross-source stitching.
  • Separate sparse-gold and exhaustive-gold modes: sparse probes should report labeled recall and source-support spot checks, never official precision.

Dashboard and Chatbot

  • Make review workflow first-class: every review card should show the exact missing support fields, stronger evidence candidates, and one-click “promote to gold/adversarial” backlog actions.
  • Keep chatbot read-only: answers can cite, compare, and explain verified/review states, but cannot approve proposals or imply unverified rules are safe.
  • Use chat_context.sqlite as the default context surface: it reduces scattered JSON joins and helps keep follow-ups pinned to the selected rule.
  • Add answer regression tests: keep the 15 policy cases, then add LLM wording spot checks for follow-up grounding, citation completeness, and refusal of unsupported approvals.

Debugging and Fixing Priorities

Immediate fixes

  • Add extraction progress logs per pack and timeout handling around model calls.
  • Retry invalid JSON packs automatically and mark non-retryable failures in the report.
  • Expose source page range, pack count, cache status, and LLM error count in the dashboard run header.
  • Add sparse-gold warning mode to evaluate_benchmark.py for exploratory cities.

High-leverage engineering

  • Build a table layout regression suite using Burnaby, Calgary, Vancouver, and Surrey page crops.
  • Track review-to-verified conversion by support gap family so M7.5 optimizes the right queue.
  • Version configs and gold sets together; every city port should have source hash, page scope, benchmark status, and known limitations.
  • Move generated run docs into a clearer artifact namespace so source docs are easier to audit.

Final Recommendation

Move to M7.5, but define it as an evidence and workflow upgrade, not a verifier relaxation. The system is strongest where it says “no” or “needs review” when evidence is incomplete. The next massive improvement is to give the verifier better structured evidence and give reviewers/dashboard/chatbot users better ways to understand and close those gaps.
