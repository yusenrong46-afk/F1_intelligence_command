Part I · Foundations

1. What you actually built, in plain words

Canadian municipalities publish zoning bylaws: long legal PDFs that say things like "the minimum lot area is 281 m²" or "the maximum building height is 11.5 m." Planners, permit reviewers, and GIS (mapping) teams need those statements as clean, structured data — rows like lot_area ≥ 281 m² — so software can check a proposed building or draw a zoning map.

Doing that by hand is slow and error-prone. Doing it with a raw large language model (LLM) is fast but dangerous: the model will confidently invent rules that aren't in the document. M7 threads the needle. It:

  1. Reads the bylaw PDF and finds the passages likely to contain rules (retrieval).
  2. Asks an LLM to propose candidate rules as structured fields — but the model is explicitly told not to decide whether a rule is correct.
  3. Verifies every candidate with plain, auditable code that checks each field against the exact cited sentence. Only candidates that survive are marked verified.
  4. Publishes the verified rules to a GIS hand-off file and a dashboard, and offers an advisory chatbot to explore the bylaw.

The product spans three pilot cities — Burnaby R1 (a compact small-scale-housing district), Calgary R-CG (buried inside a 1,053-page omnibus bylaw), and Vancouver RS — proving the approach generalizes rather than being hand-fit to one document.

✓ Why this framing matters

The whole system is organized around one trust boundary: the line between "a machine guessed this" and "code proved this against the source." Once you see that boundary, every file in the repo falls into one of two roles — a proposer (allowed to be creative, never trusted) or a verifier / measurement component (boring, deterministic, the only authority).

2. The problem, and why it is genuinely hard

  • Bylaws are long and messy. Calgary's runs 1,053 pages. Rules hide in flowing prose and in dimensional tables — grids of dwelling-type × unit-count × value. A naive text reader misses most of the table rules entirely.
  • The same number means different things. "1.2 m" might be a side-yard setback, an easement width, or a fence height. Bind it to the wrong concept and you publish a false rule that looks perfectly plausible.
  • LLMs hallucinate. Even with retrieval, 2025-era AI legal tools still fabricate or mis-attribute roughly 17–33% of citations. You cannot ship raw model output as if it were law.
  • The cost of a wrong rule is asymmetric. A missed rule is an inconvenience (a human fills the gap). A wrong "verified" setback could mis-approve a building. So M7's number-one job is never to verify something the bylaw doesn't say — even at the cost of parking some true rules in a human-review queue.
◆ Core idea — asymmetric risk

M7 is deliberately biased toward caution. A false "verified" is a catastrophe; a rule held for review is just unfinished work. Every design decision downstream follows from that asymmetry.

3. Python catch-up — the language features in this codebase

You wrote (or generated) a lot of modern, type-annotated Python. Here is a tour of the constructs you'll actually see in M7's files, each with a real snippet. Expand only what you need.

Type hints: list[str], dict[str, Any], | None used everywhere

Python doesn't enforce types at runtime, but annotations document what a function expects and lets tools catch mistakes. In M7 you'll see signatures like def verify_candidates(config, evidence_units, rule_candidates) -> dict[str, list[dict[str, Any]]].

  • list[str] — a list whose items are strings.
  • dict[str, Any] — a dictionary whose keys are strings and whose values can be anything. This is the "JSON object" shape used for every rule.
  • X | None — "an X, or nothing." The verifier uses evidence: dict[str, Any] | None because a candidate might cite an evidence id that doesn't exist.
  • from __future__ import annotations at the top of each file makes all annotations lazy strings, so you can write list[str] on older Pythons without errors.
frozenset and set algebra — the heart of the decision policy decision_policy.py

A set is an unordered collection of unique items with fast membership tests and algebra: A - B (difference), A & B (intersection), A | B (union). A frozenset is just a set that can't be modified after creation — perfect for a fixed catalog of rule-codes that should never change at runtime.

M7's entire safety verdict is three set operations:

blocking = set(support_gaps) - ADVISORY_GAPS   # drop advisory-only flags
if not blocking:                 return VERIFIED   # nothing left to object to
if CRITICAL_REJECTION_GAPS & blocking: return REJECTED   # any hard contradiction?
if NOT_USED_GAPS & blocking:     return NOT_USED   # not an enforceable rule
return REVIEW_NEEDED                               # plausible, but unproven

That's it. The "AI" makes none of this decision — it's four lines of set math you can read aloud.

Regular expressions & the digit-boundary trick support_checks.py

A regex is a tiny pattern language for finding text. M7 leans on it heavily, and one detail matters for safety: when checking whether the value 5 appears in evidence, you must not match the 5 inside 7.5 or inside a section reference like 101.5.2. The code uses a "negative look-behind / look-ahead" — (?<![\d.])5(?!\.?\d) — meaning "a 5 with no digit-or-dot immediately before or after it." Without this boundary, a candidate value of 5 would be falsely "found" in unrelated numbers, and a hard-rejection gate would silently pass.

Comprehensions, f-strings, pathlib, JSON ↔ dict everywhere
  • List/dict comprehension — [r for r in rules if r["status"] == "verified"] builds a new list in one line; the verifier uses these to split candidates into buckets.
  • f-string — f"{value} must be <= {limit}." embeds variables directly inside a string.
  • pathlib.Path — the modern way to handle file paths: Path(run_dir) / "verified_rules.json".
  • JSON ↔ dict — json.load(f) turns a file of text into Python dicts/lists; json.dump() writes them back. Every artifact M7 produces is a JSON file, and in Python each rule is just a dict.

4. ML / CS catch-up — the concepts behind the magic

These are the ideas the AI-generated code quietly relies on. Each box ends with where it lives in M7 so you can connect concept to file.

Deterministic vs probabilistic — the most important distinction in the whole project core

A probabilistic system (an LLM) can give different answers to the same input and is "usually right." A deterministic system always gives the same output for the same input and is "provably consistent." M7's design insight is to use the probabilistic part only where creativity helps (finding candidate rules) and the deterministic part wherever correctness is non-negotiable (deciding what's true).

Where in M7: the LLM extractor is probabilistic (native_extraction.py); the verifier and decision policy are 100% deterministic (verification.py, decision_policy.py, support_checks.py).

What an LLM is, and why it hallucinates extraction

A large language model predicts the next token (a word-piece) given the previous ones. It has no notion of "true" — only "plausible continuation." When it doesn't know, it produces fluent, confident text anyway. That's a hallucination. For legal text this is fatal: the model will happily write a setback value that reads like the bylaw but isn't in it.

Where in M7: the entire verification layer exists because of this. The LLM proposes; it is never believed.

Embeddings, RAG, BM25, dense vectors, RRF — how M7 "finds the right passage" bylaw_rag.py

RAG (retrieval-augmented generation) means: before asking the LLM anything, fetch the most relevant source passages and feed only those to the model, so it answers from real text instead of memory.

  • BM25 — a classic keyword-ranking formula (the same family search engines used for decades). Fully deterministic, no model download. Great at exact words, blind to synonyms.
  • Embeddings / dense vectors — a neural model turns each passage into a list of numbers (a "vector") so that passages with similar meaning sit near each other, even with different words. M7 can optionally add this leg (baai/bge-m3).
  • Hybrid + RRF — M7 runs BM25 and (optionally) dense retrieval, then fuses their rankings with Reciprocal Rank Fusion: score += 1 / (60 + rank). A passage ranked highly by either method floats to the top. The constant 60 is the standard RRF k.
  • Reranker / cross-encoder — a heavier model (cohere/rerank-4-fast) that re-scores the top candidates by reading the query and passage together, catching subtle relevance the first pass missed.

Where in M7: bylaw_rag.py builds the index and does BM25+RRF; the deterministic query-expansion (mapping "tall"→"height") closes BM25's synonym gap without any model.

JSON-schema-constrained extraction native_extraction.py

Rather than parse free-form prose, M7 asks the model to return a strict JSON object (response_format: {"type":"json_object"}, temperature: 0). This forces the output into the exact field shape the verifier expects — {rule_object, value, unit, operator, scope, ...} — and removes a whole class of parsing bugs.

Precision vs recall, gold sets, adversarial tests benchmark/

Precision = of the rules we marked verified, what fraction are actually correct? Recall = of all the true rules, what fraction did we capture? They trade off. M7 pins precision at 1.00 (every verified rule is correct) and treats recall as the thing to grow — but only via better extraction, never by loosening the verifier.

  • Gold set — a hand-written list of the correct rules for each city (e.g. 40 for Burnaby), authored independently so the benchmark isn't grading its own homework.
  • Adversarial tests — deliberately tricky candidates (inverted operators, easement widths, ranges) that must be blocked. M7's suites block 24/24 (Burnaby), 6/6 (Calgary), 4/4 (Vancouver).
Part II · The big idea

5. The thesis: propose-then-verify

Most "AI reads documents" projects fail at exactly one point: they believe the model. M7's central bet is that you can keep an LLM's recall and creativity while eliminating its risk — by demoting it to a proposer and putting a deterministic verifier in charge of every published claim.

Concretely, the LLM is told in its own system prompt: "You extract zoning rule candidates from quoted bylaw text. Return only valid JSON. Do not decide whether a rule is correct." The phrase "do not decide" is load-bearing. The model's job ends at suggestion.

◆ Core idea — the trust boundary

There is exactly one line in the system where "a machine guessed" becomes "code proved it against the source." Nothing the proposer attaches — no confidence score, no "I'm sure" flag, no model label — can carry a rule across that line. Only the deterministic gates can.

This is why a high-recall but occasionally-wrong model is safe to use here: its mistakes can only ever cost recall (a true rule held for review), never precision (a false rule published). The verifier is the circuit breaker.

Part III · Stage by stage

8. Stage 1 — Extraction (the proposer)

Stage 1's only job is to surface candidate rules with the exact source text that justifies them. It is allowed to be wrong; the verifier is the safety net. Four moving parts:

8.1 Page-scoping — don't read 1,053 pages when you need 3

For a huge omnibus bylaw (Calgary), reading everything floods retrieval with numbers from unrelated districts. When a provenance.json pins the relevant page range, restrict_intermediate_to_pages() clips the document before retrieval, while preserving the original page numbers so citations stay honest. This single fix is why Calgary's recall jumped (more on that in §13).

8.2 Hybrid retrieval — finding the right passage deterministically

M7 indexes the bylaw and ranks passages with BM25 (a deterministic keyword score), optionally fused with a dense-embedding ranking via Reciprocal Rank Fusion. Because BM25 is synonym-blind, a small deterministic query expansion maps colloquial words into the corpus vocabulary ("tall" → "height") using the verifier's own shared word lists — so expansion never invents meaning, it only widens the net.

The fusion itself is four lines — note the deterministic tie-break that makes the same question always return the same clauses:

def search(self, question, *, top_k=5):
    bm25_rank  = self._bm25_ranks(question)     # {chunk_index: rank}
    dense_rank = self._dense_ranks(question)    # or None (BM25-only)
    fused = []
    for index, chunk in enumerate(self.chunks):
        score = 0.0
        if index in bm25_rank:  score += 1.0 / (RRF_K + bm25_rank[index])
        if dense_rank and index in dense_rank:
                                score += 1.0 / (RRF_K + dense_rank[index])
        if score > 0.0:  fused.append((score, chunk))
    fused.sort(key=lambda it: (-it[0], str(it[1]["chunk_id"])))  # deterministic
    return [chunk for _, chunk in fused[:top_k]]

9. Stage 2 — Verification (the heart of the system)

Everything important happens here. verify_candidates() takes the config, the evidence units, and the candidates, and returns them sorted into buckets. Its own docstring describes a four-step loop:

  1. Look up the cited evidence by id (a missing id is itself a hard-rejection gap).
  2. Normalize the candidate and enrich evidence with parent-clause context for enumerated sub-items.
  3. Collect support_gaps — run every deterministic check and record each failure as a named code.
  4. Decide — hand the gap list to decision_policy, which returns the bucket.

9.1 The field gates — "is this exact claim visible in the cited sentence?"

These are narrow, evidence-facing yes/no checks. They never extract and never promote; they only answer questions. Three are worth seeing because each closes a real failure mode.

Value check (digit-boundary). A candidate value must literally appear in the cited text — and "5" must not be satisfied by "7.5". This feeds a hard-rejection gate, so a sloppy substring match would let false citations through:

def contains_value(evidence_text, value):
    """Every value token must appear with digit boundaries — '5' is not '7.5'."""
    tokens = _value_tokens(value)            # "281" -> ["281"]
    if not tokens:
        return True
    normalized = evidence_text.replace(",", "")
    return all(token_visible(normalized, token) for token in tokens)

Operator check (default-closed). The operator must be backed by the evidence's wording — "maximum"/"not exceed" for <=, "minimum"/"at least" for >=. If a future operator is added with no wording branch, the function returns False rather than silently passing:

if operator in {"<=", "max", "maximum", "not_exceed"}:
    return any(p in text for p in ["maximum", "not exceed", "up to", "limited to"])
if operator in {">=", "min", "minimum", "at_least"}:
    return any(p in text for p in ["minimum", "not less", "at least", "shall have"])
# ... explicit branch per operator ...
return False   # default-closed: never verify an operator with zero evidence wording

Imperial-unit hold. A rule stated in feet on a metric family is never silently compared to a metre threshold and never auto-converted — that would forge source fidelity. It is routed to review:

IMPERIAL_UNIT_TOKENS = frozenset({
    "ft", "ft.", "feet", "foot", "'", "in", "inch", "inches", '"',
    "sf", "sq ft", "acre", "acres", "mile", "miles",
})
def is_imperial_unit(unit):
    return str(unit or "").strip().lower() in IMPERIAL_UNIT_TOKENS

9.2 The shape gates — "the value is present, but the sentence means something else"

The subtlest false-verifies pass every field check: the value, unit, and scope words really are in the evidence. evidence_shape_gaps() reads the shape of the sentence carrying the value and catches three classes that are otherwise invisible:

  • definition_not_rule — the value sits inside a defined-term sentence ("corner parcel" means … not exceeding 135 degrees). Vocabulary, not a regulation.
  • allowance_trigger_threshold — the value is the threshold that unlocks an allowance ("no maximum … where … 3.0 m"), or — the famous case — an easement width that reduces a setback to zero (see §13).
  • range_bound_not_maximum / coefficient_operand_not_value — a flattened range ("1 to 3 Units; 4 to 6 Units") or a ratio coefficient ("0.25 multiplied by the site area") mis-read as an absolute cap.
✗ Pitfall these gates close

Every one of these is a real number in the real text — so a keyword or substring verifier would happily publish it. They are review-or-reject only because the deterministic gates read the surrounding clause structure, not just the digits.

9.3 Two proof routes: text-span vs matrix-anchor

Prose evidence is proven by text-span checks (the gates above). Table evidence can additionally carry a matrix anchor — recovered table geometry — letting the verifier prove a value belongs to a specific column, not just that it appears somewhere in the row. We unpack that in §11.

10. From gaps to buckets — the decision policy

The verifier produces gaps; decision_policy.py is the only place that turns gaps into a verdict. Keeping it isolated makes the safety policy auditable in one screenful. There are four named catalogs of gaps (all frozensets) and one tiny function.

And the function that consumes them — short enough to read in full:

def verification_decision_from_gaps(support_gaps):
    gaps = set(support_gaps)
    blocking = gaps - ADVISORY_GAPS          # advisory flags can never veto
    if not blocking:                  return VERIFIED
    if CRITICAL_REJECTION_GAPS & blocking:  return REJECTED
    if NOT_USED_GAPS & blocking:      return NOT_USED
    return REVIEW_NEEDED                      # plausible but unproven
◆ Core idea — the tiering rationale

A scope/operator/direction miss lands in review: these are "absence-of-cue" heuristics with limited recall, so a miss usually means "wording not recognized," which a human can repair. But a value or unit absent from the cited evidence is a hard rejection: the citation itself is wrong, and no amount of context can make a number that isn't in the evidence safe to publish.

11. The matrix path & config-as-policy

Most of Burnaby's dimensional rules — lot widths, coverages, heights — live in a table, and roughly four out of five verified Burnaby rules come from the matrix path rather than prose. Linearized table text loses the column structure: the page text contains every column's words, so word-overlap can neither prove nor refute which column a value came from. Only geometry can.

11.1 Matrix anchors — recovering the grid

table_matrix.py reads the city's cached, hash-pinned source PDF with pdfplumber, recovers the column bands (x-ranges under each header), and attaches a matrix_anchor to a table evidence unit — but only on a unique row match. An ambiguous match attaches nothing.

✓ Why "inert, never guessing" matters

The anchor layer is purely additive: with no PDF it attaches nothing and the verifier falls back to text-span proof, so prose-only cities keep working. It is "allowed to be inert, never allowed to guess" — exactly the conservative posture the whole system takes.

11.2 Config as policy — the knobs that made 280 m² divergent

Each city has a JSON config that encodes policy, not code. Three knobs are doing real safety work in our example:

"rule_family_direction": {            // which way each family must point
  "lot_area": "min", "setback": "min", "building_separation": "min",
  "height": "max", "storeys": "max", "lot_coverage": "max",
  "dwelling_units": "max"
},
"structured_table_scope_patterns": [  // quarantine degraded duplicates
  { "rule_object": "setback", "all_terms": ["interior side yard", "1.2"],
    "not_terms": ["end"], "action": "review",
    "note": "1.2 m is the end-unit exception; without 'end' it's a
             degraded duplicate of the 0 m base — hold for review" }
],
"cross_family_sibling_groups": [ ["lot_coverage", "impervious_surface"] ]

That first knob is exactly why our 280 m² "maximum lot area" is held: the city declares lot_area a minimum family, so a <= reading raises rule_family_direction_mismatch. The second knob shows the system quarantining a value (1.2 m interior side yard) that would otherwise be a plausible-but-degraded duplicate — policy expressed as data, reviewable by a planner without touching Python.

13. The C5 lesson — the most important thing in this whole project

This section is the one to internalize, because it is the temptation you (or a future maintainer) will feel most strongly: "recall is only 0.82 verified — let me loosen the verifier a little to push more rules through." M7 tried exactly that, measured the result, and reverted it. Here's the story in three acts.

13.1 The easement bug — a value that's real but means the opposite

Calgary R-CG §539(4) says, roughly: "the minimum building setback from a side property line may be reduced to a zero setback where … a 1.2 metre private maintenance easement" is provided. A keyword extractor sees "setback … 1.2 metre" and proposes setback ≥ 1.2 m. But the 1.2 m is the easement width that unlocks a zero setback — verifying it would publish a 1.2 m minimum side setback the bylaw never states. The fix is a deterministic shape gate: hold when every occurrence of the value is glued to "easement" (the real correct setbacks elsewhere are not, so they still verify).

# s.539(4): a setback value bound to "easement" is the easement WIDTH that
# unlocks a (zero) setback — not the setback itself. Hold it.
if str(candidate.get("rule_object")) == "setback" and all(
    re.search(r"\beasement\b", lowered[occ.end(): occ.end() + 45]) for occ in occurrences
):
    gaps.append("allowance_trigger_threshold")

13.2 The range-bound leak — a lower bound masquerading as the cap

A flattened table row "1 to 3 Units; 4 to 6 Units" was mis-extracted as dwelling_units ≤ 3 for the lot, when the lot maximum is actually 6. The guard (range_bound_not_maximum) holds a count whose value is not the largest same-family value the source region offers, unless the scope carries a disambiguator (front/rear/accessory). Real value, wrong role → review, never verify.

13.3 The reverted rescue — why recall is never bought with looser gates

The "C5" attempt tried to lift recall by auto-promoting single-source, consensus-held review rules straight to verified. The count went up — and a ground-truth audit found it had injected real false-verifies (a separation distance borrowed from a height clause; the range-bound count above). It was reverted in full.

◆ Core idea — the rule for all future work

Raise recall by improving extraction and evidence assembly, never by relaxing the verification gates. Scored coverage is grown by giving the verifier better, more complete evidence — not by lowering the bar it has to clear.

14. Honest measurement — the scored legal-slot denominator (M7 scored)

"How much of the bylaw did we cover?" is a trap question, because the denominator is easy to game. Count every numeric signal in the corpus and your coverage looks tiny; count only what you found and it looks perfect. M7 scored defines a denominator you can defend.

A legal slot is a distinct enforceable rule. M7 scored keeps only slots that are corpus-derived (never the verifier's own outputs — otherwise the denominator would be a function of the numerator), of a recognized family, and inside the city's GIS contract. Then it collapses duplicates by legal identity:

def slot_is_scored(slot):
    """Corpus-derived, known family, and inside the GIS contract."""
    if not is_source_denominator_slot(slot):              return False
    if normalize_family(slot["rule_family_signal"]) in NOISE_FAMILIES:  return False
    return slot["gis_contract_relevance"] == "in_gis_contract"

def legal_slot_key(slot):
    """One legal rule = (family, value, unit). Scope is deliberately excluded —
    source-inferred scope is greedy on table cells, so keying on it would both
    fracture true matches and inflate the count. Scope CORRECTNESS is enforced
    by the verifier's gates, not by this measurement."""
    return (normalize_family(slot["rule_family_signal"]),
            normalized_number(slot["value"]),
            normalize_unit(slot["unit"]))

✓ Why exclude scope from the legal key

Source-inferred scope is "greedy" — a value in a multi-column yard row picks up "front" from a neighbouring column. Keying the denominator on scope would both split true matches and mislabel slots. So the measurement ignores scope (a documented, mildly coverage-inflating approximation), while scope correctness stays enforced exactly where it must be: the verifier's deterministic gates.

The pipeline emits a family of JSON artifacts. Three matter most, and they have different jobs:

A verified rule is projected to the slim contract by project_gis_contract_rule(), which strips internal traces and keeps a clean citation. Part VI · Reflection

18. Why it's good — the genuine breakthroughs

Stripped of hype, here is what is actually novel and well-built about M7:

  1. A deterministic sole-authority gate with a provable zero-false-verify guarantee. Pure-LLM legal extractors hallucinate 17–33% of citations; M7's verified set has a measured false-verify rate of zero across three cities, because no probabilistic signal can promote a rule. The guarantee is structural, not statistical.
  2. Deterministic matrix extraction. Recovering table geometry turns each (row × column) cell into an independently provable candidate — the source of roughly 4 in 5 verified Burnaby rules, and a capability most text-only RAG systems simply don't have.
  3. Honest measurement. The scored legal-slot denominator (§14) refuses to grade its own homework: it excludes the verifier's own outputs and reports a conservative 0.318, not a flattering 100%. Independently-authored gold and a literal PDF audit back it up.
  4. Leak classes captured as named, tested gates. Operator inversion, easement width, range-lower-bound, foreign unit, definition sentence, allowance trigger — each is a one-line auditable rule plus a regression test, so a closed bug can never quietly reopen.
  5. Cross-city generalization with one unchanged verifier. Burnaby, Calgary, and Vancouver share the same verification code; only the JSON config (policy-as-data) differs. The system isn't overfit to one bylaw.

19. Honest limitations & how to improve

The project is deliberately candid about what it doesn't do. None of these are verifier bugs — they are recall and provenance limits, and the fixes all live upstream of the trust gate.

LimitationWhy it existsThe right lever
Recall capped — some true rules sit in review (heritage conditionals, single-source prose).By design: promoting them risks false-verifies (the C5 lesson).Better evidence assembly, not looser gates.
Modest scored coverage (Calgary, Vancouver lower than Burnaby).Extraction is still incomplete on table-heavy / sparse-gold districts.Richer table-proof completeness; larger authored gold for Vancouver.
Provenance labels can lag (a row cites §534 where the clause is §535).Section attribution happens at extraction; value/page stay correct.Refactor the section-attribution step in extraction.
One Burnaby fire rule (br1_fire_003) stays unverified.Non-deterministic / hard-to-anchor evidence.Targeted evidence repair for single-source prose families.

Concrete next levers (a to-do list for future-you)

  • Strengthen evidence assembly for review rules — build more complete evidence packs so the verifier has enough to prove scope/condition, moving rules from review to verified without changing a single gate.
  • Deepen matrix proof — better header-band binding, continuation-row merging, and branch (conditional-cell) semantics, so more table cells become provable.
  • Expand Vancouver gold — systematically author the principal/duplex/triplex sections so the benchmark denominator reflects reality.
  • Shadow-evaluate frontier methods — try retrieval/RAG scoring upgrades (e.g. LegalBench-RAG-style metrics, table-image retrieval) in a shadow lane; adopt only if they beat the safety gates first.
  • Fix provenance attribution — decouple the section label from the value so citations are exact.
◆ The mental model to keep

Every future improvement is a question of "can the verifier now prove more, because we gave it better input?" — never "can we make the verifier accept more?" Keep that distinction and the safety contract survives every change you make.

20. Glossary

Adversarial test
A deliberately tricky candidate (inverted operator, easement width, flattened range) that the verifier must block. M7 blocks 24/24 (Burnaby), 6/6 (Calgary), 4/4 (Vancouver).
BM25 §8
A classic, deterministic keyword-ranking formula used for retrieval. Exact-word strong, synonym-blind.
Candidate
A proposed rule from extraction, before verification. Allowed to be wrong.
Deterministic §4
Same input always yields the same output. The verifier and decision policy are fully deterministic.
Embedding §4
A numeric vector representing a passage's meaning, so semantically similar text sits nearby.
Evidence unit
A cited chunk of source text (with page, type, and optional matrix anchor) that a candidate points to.
frozenset §3
An immutable Python set. Used for the fixed gap catalogs so the safety policy can't mutate at runtime.
Gold set §4
A hand-authored list of correct rules per city, used to measure recall/precision independently.
Hallucination §4
Fluent, confident, but unsupported model output. The reason the verifier exists.
Legal slot §14
A distinct enforceable rule, keyed by (family, value, unit). The honest coverage denominator.
Matrix anchor §11
Recovered table geometry (column bands, branches) attached to table evidence, enabling column-level proof.
Precision / recall §4
Precision = fraction of verified rules that are correct (pinned at 1.0). Recall = fraction of true rules captured (the thing to grow).
Proof trace
The per-field record (evidence quote + reason) explaining why each claim was supported. Lives in verified_rules.json.
RAG §4
Retrieval-augmented generation — fetch relevant passages first, then have the model answer only from them.
Reranker / cross-encoder §8
A heavier model that re-scores top retrieval hits by reading query and passage together.
RRF §8
Reciprocal Rank Fusion — combine multiple rankings via 1/(60+rank).
Support gap
A named code recorded when a deterministic check fails. The decision policy maps the gap set to a bucket.
Trust boundary §5
The single line between "AI proposed" and "code proved." Nothing probabilistic crosses it.
